# 0003. Структура: модульний моноліт за доменами з публічним `index.ts`

- Status: accepted
- Date: 2026-11-14

## Context

Структура коду має виводитися зі spec (§3 модулі, §4 дані), а межі модулів мають бути
обґрунтовані й перевірювані. Далі модулі обростуть БД (2), тестами (3), а один із них
стане бібліотекою (5).

## Decision Drivers

- один модуль spec = одна тека, щоб аудит «структура ↔ spec» був механічним;
- межі мають перевірятися автоматично, а не лише домовленістю;
- модуль `standings` має виноситися в бібліотеку без переписування (завдання 5).

## Considered Options

1. Шари: `controllers/`, `services/`, `repositories/` (MVC за типом файлу)
2. Модулі за доменами: `modules/<name>/{routes,service,repository,domain,index}.ts`
3. Мікросервіси на кожен модуль

## Decision

Обрано **модулі за доменами**. Кожен модуль експортує публічний API лише через `index.ts`.
Правила D1–D3 зі spec перевіряє dependency-cruiser (`npm run audit:deps`).

## Pros and Cons of the Options

### Шари (MVC за типом файлу)

- 👍 звично (так було в GoIT-проєктах)
- 👎 модуль spec «розмазаний» по трьох теках, тож межу між `matches` і `teams` неможливо
  перевірити правилом
- 👎 винести модуль у бібліотеку можна лише збираючи файли з усіх шарів

### Модулі за доменами

- 👍 тека відповідає модулю spec, а правило «тільки через `index.ts`» перевіряється автоматично
- 👍 `standings` (чисті функції) виноситься в пакет як є
- 👎 трохи більше файлів-обгорток (`index.ts`)

### Мікросервіси

- 👍 жорсткі межі на рівні мережі
- 👎 для одного розробника і MVP це надмірно: деплой, мережеві помилки, узгодженість даних

## Consequences

- Позитивні: порушення меж ловиться в pre-push, а аудит зводиться до звіту
  dependency-cruiser.
- Негативні: міжмодульні виклики йдуть лише через публічні функції, без прямого доступу до
  чужих репозиторіїв (це навмисно).
- Далі: у завданні 2 кожен `*.repository.ts` отримає реалізацію з БД за тим самим контрактом.
