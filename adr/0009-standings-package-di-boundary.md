# 0009. Таблиця — окремий пакет із DI: межа модуля, порти й кеш

- Status: accepted
- Date: 2026-11-18

## Context

Базова лінія завдання 5 ([spec-lab5 §5](../spec-lab5.md)) показала, що найбільший внесок у
час сервера дає `GET /tournaments/:id/standings` (L1, 50 % трафіку). На кожне читання
модуль `standings` робив 4 послідовні SQL через сервіси трьох модулів, тягнув усі матчі
турніру, щоб відфільтрувати завершені в JS, і перераховував таблицю, хоча вона змінюється
лише після запису результату (5 % трафіку). SQL сам по собі швидкий (< 0,4 мс в `EXPLAIN`),
тож на стейджі час іде на мережеві round trip до Neon. Завдання вимагає винести такий модуль
в окрему бібліотеку з DI і типізованим контрактом.

## Decision Drivers

- пакет не знає про БД, express і застосунок, щоб його можна було перевикористати й тестувати окремо;
- менше round trip на L1 без порушення інваріантів, якими володіють інші модулі;
- таблиця після запису результату одразу актуальна (S3) і не зберігається в БД (spec §4);
- просте налаштування збірки без окремого реєстру пакетів;
- межу перевіряє машина (dependency-cruiser), а не домовленість.

## Considered Options

1. Лишити модуль у `src/`, лише об'єднати запити
2. Пакет `packages/standings` (npm workspaces) з портами `StandingsSource`, `StandingsCache`,
   `Clock`, `PointsRules`; реалізації дає composition root
3. Матеріалізована таблиця в БД, яку оновлює запис результату (тригер чи сервіс)
4. Окремий npm-пакет у реєстрі

## Decision

**Варіант 2.** Пакет `@tournament-planner/standings`, чистий TypeScript без runtime-залежностей.
Контракт (`contract.ts`): знімок `{ teams, results }`, рядок таблиці, порти. Фабрика
`createStandings({ source, rules?, cache?, clock?, ttlMs? })`. Повертає `undefined` для
неіснуючого турніру, а мапінг у 404 робить застосунок.

Реалізації портів у застосунку:

- `createPgStandingsSource(db)` — read model, **один** SQL з `json_agg`, лише завершені
  матчі. Це свідомий read-only виняток із D2 (spec-lab5 §5);
- `createServicesStandingsSource(...)` — через сервіси модулів для `DATA_SOURCE=static`;
- `createMemoryCache()` і `systemClock` з пакета. Кеш можна замінити іншою реалізацією порту.

Інвалідація — у composition root: обгортки `registerTeam` і `recordResult` викликають
`standings.invalidate(tournamentId)` після успіху (тобто після коміту). Модулі `tournaments`
і `matches` про `standings` не знають (D4). Лічильник поколінь не дає читанню, що почалося
до запису, покласти в кеш стару таблицю.

Резолюція пакета: `exports` з умовою `tp-source` → `src/index.ts` для `tsc`, tsx і
dependency-cruiser, `default` → `dist/` для `node` у проді. Vitest бере джерело через alias.
`npm run build` спершу збирає пакет.

Правила: **D10** — пакет не імпортує `src/`, npm-залежності й модулі Node; **D11** —
застосунок імпортує лише точку входу пакета.

## Pros and Cons of the Options

### Лишити в `src/`, об'єднати запити

- 👍 найменше змін
- 👎 не виконує вимогу про окрему бібліотеку з DI
- 👎 перерахунок на кожне читання лишається

### Пакет із портами (обрано)

- 👍 пакет тестується без БД (100 % покриття, тести з керованим годинником)
- 👍 L1 = 1 SQL на холодний кеш і 0 з кешу; межу перевіряють D10/D11
- 👎 read model читає таблиці інших модулів, тож це зв'язність зі схемою (її ловлять
  інтеграційні тести на PGlite і PostgreSQL 16)
- 👎 кеш у пам'яті процесу: на кількох інстансах застарілість до TTL (5 с за замовчуванням)

### Матеріалізована таблиця в БД

- 👍 читання без обчислень на будь-якій кількості інстансів
- 👎 суперечить spec §4 («таблиця не зберігається»), потребує міграції та узгодження записів
- 👎 логіка S4 переїжджає в SQL або в шлях запису

### Пакет у реєстрі

- 👍 справжнє версіонування
- 👎 публікація, токени, синхронізація версій заради одного споживача

## Consequences

- Позитивні: L1 без зайвих round trip; модуль перевикористовуваний і замінюваний
  (інше джерело, Redis-кеш, інші правила очок) без змін у пакеті.
- Негативні / ризики: читання таблиць інших модулів (виняток D2); на кількох інстансах
  таблиця може бути застарілою до `STANDINGS_CACHE_TTL_MS`. Якщо інстансів стане більше —
  спільний кеш або подія інвалідації.
- Повернутися до попереднього стану: `STANDINGS_CACHE_TTL_MS=0` вимикає кеш без деплою коду.
