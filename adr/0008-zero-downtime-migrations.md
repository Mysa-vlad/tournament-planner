# 0008. Міграції без простою: expand/contract, окремі кроки, readiness замість міграцій на старті

- Status: accepted
- Date: 2026-11-14

## Context

На стейджі під час деплою деякий час працюють дві версії: стара обслуговує трафік, нова
стартує. Обидві бачать одну БД. Якщо міграція ламає стару версію або виконується на старті
нової з таймаутом, маємо простій або цикл «таймаут → падіння → рестарт».

## Decision Drivers

- стара версія коду має працювати з новою схемою, поки трафік не перемкнуто;
- довгі операції (індекси на великій таблиці) не мають блокувати ні записи, ні старт;
- нова версія не повинна отримати трафік до готовності;
- кожен крок має бути ідемпотентним, щоб повтор CD був безпечним.

## Considered Options

1. Міграції під час старту застосунку (як було з PGlite)
2. Окремі кроки в CD перед деплоєм + expand/contract + readiness-перевірка
3. Інструмент міграцій (node-pg-migrate / Flyway) з тими самими принципами

## Decision

**Варіант 2.** Каталоги `migrations/schema` (блокуючі DDL, лише expand: нові таблиці або
колонки, nullable чи з default), `migrations/data` (backfill пачками) і `migrations/indexes`
(`CREATE INDEX CONCURRENTLY IF NOT EXISTS`, поза транзакцією). Seed (`npm run db:seed`) —
не міграція. CD виконує кроки в цьому порядку **до** деплою. Contract (видалення старих
колонок) — окремий наступний реліз, коли жодна версія їх уже не читає. На PostgreSQL-сервері
застосунок під час старту не мігрує. `/health/ready` дає 200 лише за доступної БД і схеми,
не старішої за ту, яку знає код, тож Render перемикає трафік лише тоді.

## Pros and Cons of the Options

### Міграції на старті

- 👍 нуль кроків у CD
- 👎 довга міграція перевищує таймаут старту, інстанс перезапускається, і так по колу
- 👎 два інстанси одночасно мігрують ту саму БД (гонка)

### Окремі кроки в CD + readiness

- 👍 індекс будується без блокування записів і без тиску таймауту старту
- 👍 явний порядок: структура до коду, що її використовує; код до contract-кроку
- 👎 дисципліна вручну: міграцію, що ламає сумісність назад, треба розбити на два релізи

### Інструмент (node-pg-migrate / Flyway)

- 👍 down-міграції, блокування від паралельного запуску
- 👎 ще одна залежність для двох файлів; принципи (кроки, expand/contract) все одно наші

## Consequences

- Позитивні: деплой не зупиняє стару версію, а новий інстанс без схеми не отримує
  трафік (перевірено тестами `deploy.test.ts`).
- Негативні: власний раннер не має блокування від паралельного CD, тому
  `concurrency: deploy-staging` у workflow серіалізує деплої.
- Далі: при першій contract-міграції додати перевірку, що жодна задеплоєна версія не
  читає колонку, яку видаляють.
