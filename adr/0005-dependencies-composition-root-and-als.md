# 0005. Керування залежностями: composition root (ручний DI) + AsyncLocalStorage для контексту

- Status: accepted
- Date: 2026-11-14

## Context

Сервісам потрібні три різні види залежностей: **ресурси** (БД, що живе весь процес),
**інші модулі** (TeamsService тощо) і **request-контекст** (ініціатор, business-process ID), що
живе один запит. Завдання забороняє протягувати 10–15 параметрів, а business-process ID має
автоматично потрапляти в кожен лог з будь-якого рівня.

## Decision Drivers

- жодного «прокидання» `userId`/`requestId`/`tx` через сигнатури функцій;
- залежності модулів видно явно (і їх перевіряє dependency-cruiser, D4);
- без магії декораторів і рефлексії; підміна для тестів має бути тривіальною.

## Considered Options

1. Протягування параметрів (`ctx` першим аргументом усюди)
2. DI-контейнер (tsyringe / awilix) для всього, зокрема request-scope
3. Composition root (фабрики) для ресурсів і модулів + AsyncLocalStorage для request-контексту
4. Effect (Effect-TS) з шаром залежностей

## Decision

Обрано **варіант 3**:

- `src/composition.ts` — єдине місце, де ресурси створюються (БД ініціалізується одразу з
  `SELECT now()`) і передаються в модулі через фабрики `createXService(deps)`;
- `src/shared/context.ts` — `AsyncLocalStorage<RequestContext>`; HTTP-middleware встановлює
  `requestId` (з `X-Request-Id` або новий UUID) і `userId` (`X-User-Id`) один раз на вході;
- логер (`pino` з `mixin`) читає контекст сам, тож `requestId`/`userId` є в кожному записі,
  зокрема в логах шару БД;
- активна транзакція теж лежить у своєму ALS (`src/db/database.ts`), тож репозиторіям не
  потрібен параметр `tx`.

## Pros and Cons of the Options

### Протягування параметрів

- 👍 усе явно, без «невидимого» стану
- 👎 рівно те, що завдання забороняє: `ctx` у кожній сигнатурі, і легко забути передати в лог

### DI-контейнер (tsyringe/awilix)

- 👍 request-scope «з коробки»
- 👎 декоратори/рефлексія, а помилки зв'язування видно лише в рантаймі
- 👎 для 4 модулів контейнер — більше коду, ніж фабрики

### Composition root + ALS

- 👍 залежності модулів явні (аргументи фабрик), а контекст запиту неявний, але в одному місці
- 👍 ALS — вбудований у Node механізм, тож контекст переживає `await` і доходить до БД
- 👎 «невидимий» стан: функція, викликана поза запитом, не має контексту (`requireUserId` кидає
  `UNAUTHENTICATED`)
- 👎 подія `res.on('finish')` може статися поза ALS, тому там значення передаються явно

### Effect

- 👍 типізовані залежності й помилки на рівні типів
- 👎 нова парадигма для всієї кодової бази, високий поріг входу для курсу

## Consequences

- Позитивні: сигнатури сервісів містять лише бізнес-параметри (`startTournament(id)`).
  Лог будь-якого рівня містить `requestId`; транзакція охоплює виклики кількох модулів без
  передачі `tx`.
- Негативні: код, що виконується поза HTTP (міграції, майбутні cron-задачі), має сам
  відкривати контекст через `runWithContext`.
- Далі: у завданні 5 фабрики стануть основою DI для винесеної бібліотеки.
