# Spec — Завдання 4: CI/CD і розгортання

Доповнює [spec.md](spec.md), [spec-lab2.md](spec-lab2.md), [spec-lab3.md](spec-lab3.md).

## 1. Намір і обсяг

Жодна зміна не потрапляє в `main` без зеленого CI, а кожен коміт у `main` сам їде на
публічний стейдж. Будь-хто може перевірити, яка версія задеплоєна (`/version`).
**Поза обсягом:** продакшн-оточення (лише стейдж), канарські релізи, відкат через UI
(відкат — це revert-коміт, що проходить той самий конвеєр).

## 2. Перевірки CI (GitHub Actions, `.github/workflows/ci.yml`)

Запуск: кожен `pull_request` у `main` і кожен `push` у `main`. Кожна перевірка — окремий
job зі стабільною назвою, і ці назви вимагає правило гілки.

| Job (обов'язковий статус) | Що перевіряє                                                            | Падає, якщо                          |
| ------------------------- | ----------------------------------------------------------------------- | ------------------------------------ |
| `commits`                 | кожен коміт PR — Conventional Commits (`scripts/check-commit-msg.mjs`)  | хоч одне повідомлення не за форматом |
| `quality`                 | Prettier (стиль), ESLint, `tsc`, межі модулів (dependency-cruiser)      | будь-яке порушення                   |
| `test`                    | unit + інтеграційні на PGlite з порогами покриття (spec-lab3 T1/T2)     | тест червоний або поріг не досягнуто |
| `test-postgres`           | інтеграційні тести на **справжньому PostgreSQL 16** (service container) | тест червоний на реальному сервері   |
| `build-e2e`               | `npm run build` + E2E проти зібраного процесу; Docker-образ збирається  | збірка чи E2E падає                  |

Мутаційне тестування (хвилини) запускається окремим workflow вручну (`workflow_dispatch`),
а звіт зберігається як артефакт.

## 3. Політика мерджа (правило для `main`)

- Зміни лише через PR, тобто прямий `push` у `main` заборонено, force-push і видалення гілки теж.
- Усі job з §2 мають бути зеленими, і гілка має бути актуальною відносно `main`.
- Об'єднання — merge-коміт (історія ітерацій зберігається, standards/commits-and-branches.md).

## 4. CD на стейдж

**Ціль:** Render (Docker web service, free) + Neon (керований PostgreSQL). Стейдж
доступний з інтернету за публічним URL.

Конвеєр `cd.yml` запускається після зеленого CI на `main` (`workflow_run`) і має кроки:

1. **Міграції структури** (`npm run db:migrate -- schema`): блокуючі DDL, лише
   **сумісні назад** (expand): нова колонка nullable або з default, без видалень і
   перейменувань. Стара версія застосунку, що ще обслуговує трафік, з ними працює.
2. **Міграції даних** (`-- data`): неблокуючі оновлення пачками, окремо від структури.
3. **Індекси** (`-- indexes`): `CREATE INDEX CONCURRENTLY` окремим кроком, без транзакції
   й без таймауту старту застосунку.
4. **Деплой**: deploy hook Render. Blue-green — нова версія отримує трафік лише після
   того, як `/health/ready` повертає 200 (БД доступна, версія схеми ≥ очікуваної). До
   того трафік обслуговує стара версія.
5. **Перевірка**: CD чекає, поки `GET /version` на стейджі поверне SHA цього коміту.

**Seed** (`npm run db:seed`) — окрема команда для демо-даних, ніколи не частина міграцій.
Застосунок під час старту на PostgreSQL **не мігрує** (лише перевіряє версію схеми). Так
немає циклу «довга міграція → таймаут → падіння → рестарт».

## 5. Критерії прийняття

- **AC18.** PR з порушенням стилю, з червоним тестом і з неправильним повідомленням
  коміту дає червоний CI, а merge заблоковано (кожен — окремий PR, посилання на прогони).
- **AC19.** Коміт у `main` автоматично деплоїться, і `GET /version` на стейджі повертає
  його SHA.
- **AC20.** `GET /health/ready` дає 503, поки БД недоступна або схема застаріла, і 200,
  коли застосунок готовий.
- **AC21.** Міграції структури, даних, індекси й seed — окремі команди. Застосунок на
  PostgreSQL не запускає міграції під час старту.
- **AC22.** Інтеграційні тести проходять і на PGlite, і на справжньому PostgreSQL.
