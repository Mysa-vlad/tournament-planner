# 04 — Аудит Завдання 2: зрізані кути, N+1, поведінка на збоях

**Метод.** Аудит вимірювальний, а не «на око»:

- `npm run probe:queries` рахує SQL-запити на одне читання для N = 4/8/16 команд (лічильник
  у request-контексті, `src/shared/context.ts`);
- `npm run probe:edge` проганяє крайові випадки на обох джерелах (static і pg).

**Принцип виправлення.** Як і в завданні 1: спершу вхід (`spec-lab2.md`), потім код, потім
регресійний тест у smoke (його запускає pre-push).

## N+1 (окремий пункт умови)

|         | N = 4 | N = 8 | N = 16 | після виправлення      |
| ------- | ----- | ----- | ------ | ---------------------- |
| розклад | 6     | 10    | 18     | **3** для будь-якого N |
| таблиця | 7     | 11    | 19     | **4** для будь-якого N |

- **Де виникла.** `matches.getSchedule` у циклі викликав `teams.getTeam(id)` для кожної
  команди, а `standings.getStandings` робив `Promise.all(teamIds.map(getTeam))`. На статичних
  даних цього не видно, бо запитів немає. Проблема проявилась лише після переходу на БД.
- **Вхід.** Правило **D9** (батч-читання) і вимірюваний **AC11** (`4e555e8`).
- **Виправлення.** `TeamsService.getTeamsByIds` → один `WHERE id = ANY($1::uuid[])` (`aa6cae0`).
- **Регресія.** `test/smoke/queries.test.ts` порівнює кількість запитів для N = 3 і N = 9.
- **Докази.** `docs/evidence/04-*`, `05-*`.

## Топ-3 зрізані кути / крайові випадки

| #   | Що було не так                                                                                                                                                          | Вхід (spec)                  | Код (fix) |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------- | --------- |
| 1   | `GET /tournaments/not-a-uuid`: на static **404**, на pg **500**. Postgres відкидає приведення до `uuid`, а помилка падала в «невідомі». Поведінка залежала від джерела. | `fd410d4` (§4, рядок про id) | `2d2d67a` |
| 2   | Тіло 200 КБ давало **500** замість 413. Обробник знав лише `SyntaxError` від body-parser, а не загальні http-errors (413/415).                                          | `e8e0fa9` (§4)               | `0c03881` |
| 3   | Повторний `close()` бази кидав `PGlite is closed`. Подвійний SIGINT давав unhandled rejection і падіння процесу під час штатної зупинки.                                | `d0e14dd` (§4)               | `43c0891` |

Альтернативи:

1. **#1.** Можна було мапити SQLSTATE `22P02` у 400 в репозиторії. Відкинуто: це валідація
   форми запиту (HTTP-рівень, D6), і вона має однаково працювати без БД. Перевірка `z.uuid()`
   у роуті, до сервісу.
2. **#2.** Можна було перелічити кожен `type` body-parser. Обрано загальне правило: 4xx з
   `expose: true` зберігає свій статус, тож нові типи помилок теж покриті.
3. **#3.** Можна було ловити помилку в `server.ts`. Обрано ідемпотентність у самому ресурсі
   (`closing ??= pg.close()`), бо `close()` викликають і тести, і shutdown.

## Відомий ризик (не виправлено, свідомо)

**Гонка «заявка під час старту».** `registerTeam` перевіряє статус і вставляє заявку двома
окремими запитами, поза транзакцією старту. Теоретично заявка, що «проскочила» між
перевіркою й комітом старту, лишиться без матчів. На PGlite (одне з'єднання, транзакції
серіалізуються) я не зміг це відтворити; паралельний прогін `register` + `start` дав
коректний результат. Ризик стане реальним із пулом `pg` (завдання 4). План: умовна вставка
`INSERT … SELECT … FROM tournaments WHERE status = 'registration' FOR SHARE` і зміна статусу
до читання заявок у транзакції старту.
