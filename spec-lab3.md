# Spec — Завдання 3: тестування

Доповнює [spec.md](spec.md) і [spec-lab2.md](spec-lab2.md). Предмет тестування — застосунок
із Завдання 2.

## 1. Намір і обсяг

Тести мають ловити реальні регресії бізнес-логіки, а не лише «проходити». Ефективність
міряємо мутаційним тестуванням, а не тільки покриттям рядків.
**Поза обсягом:** навантажувальні тести (завдання 5), тести UI (його немає), контрактні
тести зовнішніх API (їх немає).

## 2. Рівні тестів

| Рівень       | Тека                | Що піднімається                                                          | Що перевіряє                                                         |
| ------------ | ------------------- | ------------------------------------------------------------------------ | -------------------------------------------------------------------- |
| Unit         | `test/unit/`        | нічого: чисті функції, сервіси з in-memory репозиторіями                 | правила домену, гілки сервісів, мапінг помилок                       |
| Інтеграційні | `test/integration/` | справжній PostgreSQL (PGlite `memory://`) + HTTP-сервер (supertest)      | SQL репозиторіїв, обмеження БД, транзакції, HTTP-контракт            |
| E2E          | `test/e2e/`         | зібраний застосунок окремим процесом (`node dist/server.js`), файлова БД | повний сценарій S1–S5 як у користувача, перезапуск, збереження даних |
| Мутаційне    | Stryker             | unit + інтеграційні тести                                                | чи падають тести, якщо зіпсувати логіку                              |

Кожен тест незалежний: окрема база `memory://` на файл тестів, без спільного стану між
файлами.

## 3. Критична логіка й пороги

Критичні модулі: `matches` (розклад S2, результат S3/S5), `standings` (таблиця S4),
`tournaments` (статуси, доступ), `http/error-handler` (контракт помилок §4 spec-lab2).

- **T1.** Повне покриття **модуля `standings`** і `matches.domain.ts`: 100 % рядків, гілок і
  функцій (unit).
- **T2.** Загальне покриття `src/` (unit + інтеграційні): гілки ≥ 85 %, рядки ≥ 90 %.
  Поріг зафіксовано в `vitest.config.ts`, тож прогін падає, якщо його не досягнуто.
- **T3.** Mutation score (Stryker) для `src/modules/**` і `src/http/error-handler.ts` ≥ 80 %,
  `break` при < 70 %. Кожен вижилий мутант класифіковано: **реальна прогалина** /
  **еквівалентний** / **прийнятний** (з причиною).
- **T4.** Знайдена прогалина закривається тестом, що вбиває конкретного мутанта. Це
  видно в повторному звіті Stryker.

## 4. Критерії прийняття

- **AC13.** `npm test` (unit + інтеграційні з покриттям) проходить і виконує T1/T2.
- **AC14.** `npm run test:e2e` збирає застосунок і проходить S1–S5 через окремий процес,
  включно з перезапуском і збереженням даних.
- **AC15.** `npm run mutation` відтворює звіт Stryker (`reports/mutation/`), а класифікація
  вижилих мутантів лежить у `docs/evidence/`.
- **AC16.** Аудит: топ-3 місця, де «зелені» тести не ловили реальний баг, кожне з окремим
  комітом-підсиленням і доказом (мутант до → вбитий після).
- **AC17.** pre-push запускає unit + інтеграційні + E2E; мутаційний прогін (хвилини) — вручну
  і в CI завдання 4.
