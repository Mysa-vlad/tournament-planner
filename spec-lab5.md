# Spec — Завдання 5: перформанс і винесення бібліотеки

Доповнює [spec.md](spec.md) і spec-lab2…lab4. Предмет — застосунок на стейджі (Завдання 4).

## 1. Намір і обсяг

Знайти боттлнеки **за вимірами**, а не за припущенням. Найвразливіший за цифрами модуль
винести в окремий пакет із DI і типізованим контрактом.
**Поза обсягом:** Lighthouse / web-vitals. У проєкті немає фронтенду (лише REST API), тож
міряти нічого, а ставити UI заради метрики — зайва вимога (DoD §5). Також поза обсягом
горизонтальне масштабування.

## 2. Сценарії навантаження (типова робота сервісу)

Типовий турнір — **16 команд** (120 матчів). Набір даних: **20 турнірів**, у кожного
завершено половину матчів. Організатор вносить рахунки, а глядачі здебільшого читають.

| ID  | Сценарій                      | Запит                            | Частка в L-MIX |
| --- | ----------------------------- | -------------------------------- | -------------- |
| L1  | глядач дивиться таблицю       | `GET /tournaments/:id/standings` | 50 %           |
| L2  | глядач дивиться розклад       | `GET /tournaments/:id/matches`   | 30 %           |
| L3  | список турнірів (головна)     | `GET /tournaments`               | 15 %           |
| L4  | організатор вносить результат | `PUT /matches/:id/result`        | 5 %            |

Окремо прогоняються L1, L2, L3, а L-MIX — змішаний профіль. L4 ідемпотентний (spec-lab2 AC9),
тому повтор того самого рахунку не змінює дані й прогін відтворюваний.

## 3. Що і як міряємо

- **Латентність і пропускна здатність:** autocannon, 10 з'єднань, 20 с, **3 повтори** на
  сценарій. Звіт містить p50 / p95 / p99, RPS, помилки, а також розкид між повторами (min–max p99).
- **CPU чи очікування:** затримка event loop (`monitorEventLoopDelay`, p99) і CPU-профіль
  (`node --cpu-prof`) з топом функцій за self-time. Висока затримка циклу означає, що
  процес зайнятий CPU; низька при високій латентності означає очікування I/O (БД).
- **RAM:** `rss` і `heapUsed` до і під навантаженням.
- **БД:** `EXPLAIN (ANALYZE, BUFFERS)` ключових запитів L1–L4 і кількість рядків.
- **Два середовища:**
  - **стейдж** (Render Free + Neon): справжня система, кожен звіт прив'язано до SHA з `/version`;
  - **локально** (PGlite, той самий набір даних): профіль і `EXPLAIN`, бо на Render Free
    профайлер недоступний.

## 4. Критерії прийняття

- **AC23.** `npm run load -- <url>` відтворює звіт (p50/p95/p99, RPS, помилки, розкид за 3
  повторами) для L1–L3 і L-MIX з SHA цілі. Звіт лежить у `docs/perf/`.
- **AC24.** `npm run profile` знімає CPU-профіль під навантаженням і друкує топ функцій.
  `GET /metrics` віддає RAM і затримку event loop.
- **AC25.** Найвразливіший модуль обрано за цифрами AC23/AC24 і `EXPLAIN`, з порівнянням
  до/після.
- **AC26.** Модуль винесено в пакет `packages/*` з публічним контрактом на TypeScript.
  Залежності (БД, кеш, годинник) передаються при ініціалізації (DI). Пакет не імпортує
  застосунок, драйвер БД чи express; це перевіряє правило dependency-cruiser **D10**.
- **AC27.** Після рефакторингу L1–L3 і L-MIX не гірші за базову лінію за p95, а
  боттлнековий сценарій — кращий.

## 5. Рішення за базовою лінією (зміна spec, вхід до рефакторингу)

Базова лінія: [стейдж](docs/perf/staging-baseline-65b30f3.md) ·
[локально](docs/perf/local-baseline-bf49300.md) ·
[CPU-профіль](docs/perf/profile-baseline-cpu-bf49300.md) · [EXPLAIN](docs/perf/explain-bf49300.md).

**Що показали цифри.**

- Усі запити в `EXPLAIN` коротші за 0,4 мс, індекси працюють. Отже, повільний не SQL сам по собі.
- На стейджі латентність росте з **кількістю послідовних запитів** до Neon (кожен — окремий мережевий round trip):
  L3 (1 SQL) має p50 71 мс, L2 (3 SQL) — 120 мс, L1 (4 SQL) — 117 мс.
- CPU-профіль: ~58 % часу займає рушій БД (PGlite у процесі), ~20 % — файловий I/O ядра Node,
  код застосунку — ~2 %. Затримка event loop локально висока (p99 ≈ 50 мс), бо PGlite рахує
  в тому самому потоці. На стейджі цей самий час стає очікуванням мережі.
- **Внесок у загальний час сервера** (частка в L-MIX × p50 на стейджі): L1 0,5 × 117 = **58,6**,
  L2 0,3 × 120 = 36,1, L3 0,15 × 71 = 10,7. Локально L1 теж найповільніший (p95 44,8 мс).

**Найвразливіший модуль — `standings`:** найбільший внесок (L1), найбільше SQL на запит (4),
залежить від трьох модулів і тягне всі ~120 матчів, щоб відфільтрувати завершені в JS,
а таблицю перераховує на кожне читання, хоча змінюється вона лише при записі результату (5 % трафіку).

**Що змінюємо.**

- **AC28.** `standings` винесено в пакет `packages/standings` (`@tournament-planner/standings`).
  Пакет залежить лише від портів зі свого контракту: `StandingsSource` (звідки дані),
  `StandingsCache` (кеш), `Clock` (годинник для TTL) і `PointsRules` (правила очок S4).
  Застосунок дає реалізації в composition root.
- **AC29.** Читання даних для таблиці — **один** SQL-запит (read model, лише завершені матчі).
- **AC30.** Таблиця кешується в пам'яті процесу. Кеш скидається після кожного запису, що
  змінює таблицю (заявка команди, результат матчу), тому S3 («таблиця зміниться при наступному
  читанні») виконується на одному інстансі. TTL (`STANDINGS_CACHE_TTL_MS`, за замовчуванням
  5000 мс; `0` вимикає кеш) обмежує застарілість, якщо інстансів кілька (blue-green під час
  деплою). Таблиця, як і раніше, **не зберігається** в БД (§4 spec.md).

**Винятки й нові правила залежностей.**

- **D2 (виняток, read model).** `standings.pg.repository.ts` читає таблиці `tournament_entries`,
  `teams` і `matches` одним read-only запитом, а не через сервіси інших модулів. Це
  свідомий виняток лише для читання: запис і інваріанти лишаються за власниками даних. Ціна —
  зв'язність зі схемою; її ловлять інтеграційні тести на PGlite і PostgreSQL 16 (AC22).
  Для `DATA_SOURCE=static` джерелом лишаються сервіси модулів.
- **D10.** Код `packages/*/src` не імпортує `src/` застосунку і жодних npm-пакетів (зокрема
  драйвер БД чи express). Пакет — чистий TypeScript без runtime-залежностей.
- **D11.** Застосунок імпортує пакет лише через його публічну точку входу
  (`@tournament-planner/standings`), а не через внутрішні файли.
